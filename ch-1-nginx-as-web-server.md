# 🚀 NGINX as a Web Server

## 🎯 Goal

Learn how NGINX serves **static files** such as:

* HTML
* CSS
* JavaScript
* Images
* Fonts
* Videos
* JSON/static assets

This is one of the fundamental things NGINX can do.

---

# 🧠 1. What is a Web Server?

A web server is software that receives HTTP requests and sends HTTP responses.

For example, a browser requests:

```text
GET /
```

The web server may respond with:

```text
index.html
```

The basic flow is:

```text
Browser
   |
   | HTTP Request
   ↓
NGINX
   |
   | finds file
   ↓
/var/www/html/index.html
   |
   | HTTP Response
   ↓
Browser
```

NGINX can act as a web server by directly serving files from the filesystem.

---

# 📦 2. Static vs Dynamic Content

This distinction is important.

## Static Content

The server sends an existing file.

Examples:

```text
index.html
style.css
app.js
logo.png
favicon.ico
```

Flow:

```text
Browser
   ↓
NGINX
   ↓
File
   ↓
Browser
```

---

## Dynamic Content

The response is generated by an application.

Example:

```text
Browser
   ↓
NGINX
   ↓
Node.js
   ↓
Database
   ↓
Response
```

For example:

```text
GET /api/users
```

Node.js might query PostgreSQL and generate JSON.

NGINX can therefore work in both situations:

```text
NGINX
 ├── Serve static files
 └── Reverse proxy to application
```

---

# 🧠 3. How NGINX Finds a Static File

Suppose the browser requests:

```text
http://localhost/index.html
```

NGINX needs to answer:

> "Which file on my filesystem corresponds to `/index.html`?"

This is controlled mainly by:

```nginx
root
location
```

For example:

```nginx
root /var/www/html;
```

Then:

```text
URL:
/index.html

Filesystem:
/var/www/html/index.html
```

---

# 📁 4. Default Web Root on Ubuntu

With a typical Ubuntu/Debian package installation:

```text
/var/www/html
```

is commonly used as the default web root.

Example:

```text
/var/www/html/
├── index.html
├── style.css
├── app.js
└── images/
    └── logo.png
```

NGINX serves files from this directory according to its configuration.

---

# ⚙️ 5. Basic NGINX Server Block

A basic static website configuration:

```nginx
server {
    listen 80;
    server_name localhost;

    root /var/www/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

This is a very important configuration to understand.

---

# 🔍 6. Understanding `server {}`

```nginx
server {
    ...
}
```

A `server` block defines how NGINX should handle requests for a particular server/listener combination.

You can think of it as:

> "For requests matching this server configuration, use these rules."

Example:

```nginx
server {
    listen 80;
    server_name example.com;

    ...
}
```

---

# 🚪 7. `listen`

```nginx
listen 80;
```

This tells NGINX to listen on HTTP port:

```text
80
```

So:

```text
http://localhost
```

normally reaches:

```text
localhost:80
```

For HTTPS, the conventional port is:

```text
443
```

---

# 🌐 8. `server_name`

```nginx
server_name localhost;
```

This tells NGINX which hostname this server block is intended to handle.

For example:

```nginx
server_name example.com;
```

would be used for requests to:

```text
http://example.com
```

You can have multiple server blocks:

```nginx
server {
    listen 80;
    server_name example.com;

    ...
}

server {
    listen 80;
    server_name api.example.com;

    ...
}
```

NGINX can then choose the appropriate server block based on the request's host information.

---

# 📂 9. `root`

```nginx
root /var/www/html;
```

This tells NGINX:

> "Use `/var/www/html` as the filesystem root for this location/server."

Suppose the browser requests:

```text
/static/logo.png
```

With:

```nginx
root /var/www/html;
```

NGINX generally maps it to:

```text
/var/www/html/static/logo.png
```

Think:

```text
URL path
   ↓
/static/logo.png

root
   ↓
/var/www/html

combined
   ↓
/var/www/html/static/logo.png
```

---

# 📝 10. `index`

```nginx
index index.html;
```

This tells NGINX which file to use when a directory is requested.

Suppose:

```text
http://localhost/
```

is requested.

NGINX sees:

```text
/
```

and can look for:

```text
/var/www/html/index.html
```

So:

```text
http://localhost/
       ↓
/var/www/html/index.html
```

---

# 📍 11. `location`

This is one of the most important NGINX concepts.

Example:

```nginx
location / {
    ...
}
```

It defines rules for a particular URI path.

For example:

```nginx
location /api/ {
    ...
}
```

handles requests beginning with:

```text
/api/
```

while:

```nginx
location /static/ {
    ...
}
```

handles:

```text
/static/
```

---

# 🧠 12. Example of Multiple Locations

```nginx
server {
    listen 80;

    location / {
        ...
    }

    location /api/ {
        ...
    }

    location /images/ {
        ...
    }
}
```

Conceptually:

```text
Request URL
     |
     ├── /api/users
     |       ↓
     |    /api/ location
     |
     ├── /images/logo.png
     |       ↓
     |    /images/ location
     |
     └── /about
             ↓
          / location
```

This allows NGINX to apply different behavior to different URL paths.

---

# 🔎 13. `try_files`

Example:

```nginx
location / {
    try_files $uri $uri/ =404;
}
```

This is extremely useful for static websites.

It tells NGINX to try several possibilities.

---

## `$uri`

```nginx
$uri
```

represents the current request URI.

For:

```text
/about.html
```

the URI is approximately:

```text
/about.html
```

NGINX checks whether the corresponding file exists.

---

## `$uri/`

The second option:

```nginx
$uri/
```

checks whether the request corresponds to a directory.

For example:

```text
/images/
```

could correspond to:

```text
/var/www/html/images/
```

---

## `=404`

If neither exists:

```nginx
=404
```

means:

> Return HTTP 404 Not Found.

So:

```nginx
try_files $uri $uri/ =404;
```

means:

```text
Try file
   ↓
Try directory
   ↓
If neither exists
   ↓
Return 404
```

---

# 🔥 14. Example of `try_files`

Filesystem:

```text
/var/www/html/
├── index.html
├── about.html
└── images/
    └── logo.png
```

Request:

```text
/about.html
```

NGINX checks:

```text
/var/www/html/about.html
```

Found:

```text
✅
```

Response:

```text
about.html
```

---

Request:

```text
/missing.html
```

NGINX checks:

```text
/var/www/html/missing.html
```

Not found.

Then:

```text
$uri/
```

doesn't produce a matching directory.

Finally:

```text
=404
```

So:

```text
HTTP 404 Not Found
```

Suppose:

```text
/var/www/html/
├── index.html
├── css/
│   └── style.css
├── js/
│   └── app.js
└── images/
    └── logo.png
```

Browser requests:

```text
GET /
```

NGINX:

```text
/
 ↓
index
 ↓
index.html
 ↓
/var/www/html/index.html
```

Browser then requests:

```text
GET /css/style.css
```

NGINX:

```text
/css/style.css
       ↓
root /var/www/html
       ↓
/var/www/html/css/style.css
```

Same for:

```text
/images/logo.png
```

which maps to:

```text
/var/www/html/images/logo.png
```

# 🔄 16. `root` vs `alias`

This is an important NGINX concept.

Both:

```nginx
root
```

and:

```nginx
alias
```

can map URLs to filesystem paths.

But they behave differently.

---

# 📂 17. `root`

Example:

```nginx
location /static/ {
    root /data/www;
}
```

Request:

```text
/static/img.png
```

maps to:

```text
/data/www/static/img.png
```

Think:

```text
root + complete URI
```

Conceptually:

```text
/data/www
     +
/static/img.png
     ↓
/data/www/static/img.png
```

---

# 📁 18. `alias`

Example:

```nginx
location /static/ {
    alias /data/www/;
}
```

Request:

```text
/static/img.png
```

maps to:

```text
/data/www/img.png
```

The `/static/` URI prefix is replaced by the alias path.

Conceptually:

```text
/static/img.png
      ↓
replace /static/
      ↓
/data/www/img.png
```

---

# 🧠 19. Easy Way to Remember `root` vs `alias`

### `root`

```text
URL:
 /static/img.png

root:
/data/www

Result:
/data/www/static/img.png
```

### `alias`

```text
URL:
 /static/img.png

alias:
/data/www/

Result:
/data/www/img.png
```

Remember:

> **root keeps the URI path.**

> **alias replaces the matching location path.**

---

# ⚠️ 20. Why `alias` Can Be Useful

Suppose your actual files are:

```text
/data/assets/
├── logo.png
└── banner.png
```

But you want users to access them through:

```text
/assets/logo.png
/assets/banner.png
```

You can use:

```nginx
location /assets/ {
    alias /data/assets/;
}
```

Then:

```text
/assets/logo.png
       ↓
/data/assets/logo.png
```

This is useful when the URL structure doesn't directly match the filesystem structure.

# 🐳 22. NGINX Static Files With Docker

NGINX can also serve files from a Docker volume.

Create a directory:

```bash
mkdir nginx-static
cd nginx-static
```

Create:

```text
index.html
```

with:

```html
<h1>Hello from NGINX in Docker!</h1>
```

Run:

```bash
docker run \
  --name web-nginx \
  -v $PWD:/usr/share/nginx/html:ro \
  -p 8080:80 \
  -d nginx
```

---

# 🧠 23. Understanding the Docker Command

The important part is:

```bash
-v $PWD:/usr/share/nginx/html:ro
```

This creates a bind mount.

Conceptually:

```text
Host
~/nginx-static/
       |
       | Docker volume mount
       ↓
Container
/usr/share/nginx/html/
```

So your host files become available inside the NGINX container.

---

# 🔒 24. What Does `:ro` Mean?

```text
:ro
```

means:

> Read Only

The container can read the files but cannot modify the mounted host files through that mount.

This is useful for static content because NGINX only needs to read the files.

---

# 🌐 25. Docker Port Mapping

The command contains:

```bash
-p 8080:80
```

This means:

```text
Host port 8080
       ↓
Container port 80
```

So:

```text
Browser
   |
   ↓
localhost:8080
   |
   ↓
Docker
   |
   ↓
NGINX container :80
```

# 📁 26. Important Difference: Ubuntu vs Official NGINX Docker

This is important for your NGINX learning.

### Native Ubuntu installation

Common paths:

```text
/etc/nginx/
├── nginx.conf
├── sites-available/
│   └── default
├── sites-enabled/
│   └── default
└── conf.d/

Web root:

/var/www/html
```

### Official NGINX Docker image

Common configuration:

```text
/etc/nginx/
├── nginx.conf
└── conf.d/
    └── default.conf
```

Common web root:

```text
/usr/share/nginx/html
```

So don't assume:

```text
/var/www/html
```

exists as the web root in every NGINX environment.

---

# 🧠 27. Why Does Docker Use `/usr/share/nginx/html`?

The official NGINX Docker image is structured differently from a typical Ubuntu package installation.

Its default static content directory is commonly:

```text
/usr/share/nginx/html
```

Therefore:

```bash
-v $PWD:/usr/share/nginx/html:ro
```

is used in the Docker example.

---

# 📄 28. NGINX Configuration Structure

The main configuration file is:

```text
/etc/nginx/nginx.conf
```

It controls global NGINX behavior.

It commonly contains something similar to:

```nginx
http {
    include /etc/nginx/mime.types;

    include /etc/nginx/conf.d/*.conf;
}
```

This means:

```text
nginx.conf
    |
    ↓
includes
    |
    ↓
/etc/nginx/conf.d/*.conf
```

So if you have:

```text
/etc/nginx/conf.d/default.conf
```

NGINX can load the server configuration from there.

---

# 🧠 29. Why `mime.types` Matters

Browsers need to know what type of content they're receiving.

For example:

```text
.html → text/html
.css  → text/css
.js   → application/javascript
.png  → image/png
```

NGINX uses MIME type configuration to send an appropriate `Content-Type` header.

Example:

```http
Content-Type: text/html
```

or:

```http
Content-Type: text/css
```

# 🧯 30. Common Error: 404 Not Found

Example:

```text
GET /logo.png
```

but:

```text
/var/www/html/logo.png
```

doesn't exist.

NGINX may return:

```text
404 Not Found
```

Check:

```bash
ls -l /var/www/html/
```

and verify your:

```nginx
root
```

or:

```nginx
alias
```

configuration.

---

# 🧯 31. Common Error: 403 Forbidden

A 403 can happen for several reasons, including filesystem permissions or directory access behavior.

Check:

```bash
ls -l /var/www/html
```

and:

```bash
namei -l /var/www/html/index.html
```

The NGINX worker process must be able to traverse the directories and read the required files.

Avoid blindly doing:

```bash
chmod 777
```

Just to make the problem disappear.

Instead, understand which user NGINX runs as and give the minimum required permissions.

# 🧠 35. NGINX as a Web Server vs Reverse Proxy

NGINX can perform both.

## Web Server

```text
Client
  ↓
NGINX
  ↓
HTML/CSS/JS files
```

## Reverse Proxy

```text
Client
  ↓
NGINX
  ↓
Node.js / Go / Python
```

## Both Together

A very common architecture:

```text
                    Client
                       |
                       ↓
                    NGINX
                  /        \
                 /          \
                ↓            ↓
          Static Files     Backend
          HTML/CSS/JS      Node/Go
```

For example:

```nginx
location / {
    root /var/www/html;
}

location /api/ {
    proxy_pass http://backend;
}
```

Then:

```text
/              → Static frontend
/css/style.css → Static file
/js/app.js     → Static file

/api/users     → Backend
/api/login     → Backend
```

This is a very important real-world NGINX pattern.

# 🚀 36. NGINX + React/Vite Frontend

Suppose you build:

```text
React/Vite application
```

After:

```bash
npm run build
```

you might get:

```text
dist/
├── index.html
├── assets/
│   ├── app.js
│   └── style.css
```

NGINX can serve the generated files:

```text
Browser
   ↓
NGINX
   ↓
dist/
```

A common configuration for a client-side routed SPA can use:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Notice the difference from:

```nginx
try_files $uri $uri/ =404;
```

The SPA version falls back to:

```text
/index.html
```

when a requested route isn't an actual file.

For example:

```text
/users
/settings
/dashboard
```

can be handled by the frontend router after NGINX returns `index.html`.

---

# 🧠 37. Why SPA Needs `/index.html` Fallback

Suppose React Router handles:

```text
/dashboard
```

The browser requests:

```text
GET /dashboard
```

But there might not be a physical file:

```text
/var/www/html/dashboard
```

Without fallback:

```text
/dashboard
    ↓
File doesn't exist
    ↓
404 ❌
```

With:

```nginx
try_files $uri $uri/ /index.html;
```

the flow becomes:

```text
/dashboard
    ↓
Does file exist?
    ↓
No
    ↓
Return index.html
    ↓
React Router handles /dashboard
```

This is one of the most useful NGINX configurations for frontend deployment.

# 🔐 38. Static Files and Security

NGINX should only expose files that are intended to be public.

Be careful with:

```text
.env
private keys
database backups
source files
configuration files
```

For example, don't place:

```text
.env
```

inside your public web root.

Bad:

```text
/var/www/html/
├── index.html
└── .env        ❌
```

Better:

```text
/var/www/app/
├── .env
└── application files

/var/www/html/
└── public files
```

The public web root should contain only files you intend users to access.

# 📊 39. Important Directives

| Directive     | Purpose                                                 |
| ------------- | ------------------------------------------------------- |
| `server`      | Defines a server configuration                          |
| `listen`      | Defines listening port/address                          |
| `server_name` | Defines hostname matching                               |
| `root`        | Defines filesystem root                                 |
| `index`       | Defines default index files                             |
| `location`    | Defines URL-specific rules                              |
| `try_files`   | Tries files/directories and fallback                    |
| `alias`       | Maps a URI location directly to another filesystem path |
| `proxy_pass`  | Sends requests to another server                        |
| `add_header`  | Adds response headers                                   |
